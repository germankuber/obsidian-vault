# 10 - System-Level Patterns for Production Readiness

> [!info] Capítulo 10 · *Agentic Architectural Patterns for Building Multi-Agent Systems* — Ali Arsanjani
> Los patrones **system-level** que dan el andamiaje de infraestructura para sistemas multi-agente production-grade: el "mundo contextual" en el que viven los agentes, no el agente en sí. Cuatro patrones — Tool and Agent Registry, Real-Time Compliance Monitoring, Agent Authentication and Authorization, Event-Driven Reactivity — más una guía estratégica de adopción progresiva. Navegá: [[_Agentic Architectural Patterns for Building Multi-Agent Systems|Mapa del libro]] · anterior [[09 - Agent-Level Patterns]].

## Resumen

Tras ensamblar los building blocks de la IA agéntica (agentes individuales con memoria y razonamiento — cap. 9; coordinación — cap. 5; robustez y accountability — caps. 6/7), este capítulo hace el shift del **agente** a la **arquitectura holística del sistema** que lo contiene: hay que construir el *mundo contextual* en el que los agentes viven y operan. La premisa: un sistema multi-agente es más que una colección de agentes; en muchos sentidos espeja una **arquitectura de microservicios moderna**, pero con una distinción crítica — en vez de servicios estáticos ejecutando código rígido, sus componentes son **agentes razonadores, goal-directed, que actúan autónomamente**. Para colaborar efectivamente y actuar como una aplicación enterprise-grade, esta inteligencia distribuida requiere una unidad completa de orquestación, adherencia a políticas e infraestructura compartida. Estos patrones atacan los requisitos no-negociables de cualquier aplicación enterprise, respondiendo: ¿cómo se descubren servicios y agentes dinámicamente? ¿cómo se imponen seguridad, identidad y control de acceso para agentes autónomos? ¿cómo se monitorea y se impone compliance en tiempo real? ¿cómo reacciona el sistema a eventos externos asincrónicamente y a escala?

El enfoque es **system-first / architecture before implementation**: primero una guía estratégica que, alineada al GenAI Maturity Model, muestra *cuándo* cada patrón se vuelve crítico a medida que el sistema evoluciona de un agente único a un ecosistema colaborativo; y un blueprint de integración que muestra *dónde* encaja cada patrón en las capas funcionales (API gateway, message bus, central registry, governance services). No es necesario ni aconsejable implementar todos los patrones para un PoC de día uno: se adoptan **progresivamente** según crecen la complejidad, el perfil de riesgo y los requisitos de escala. Los cuatro patrones — **Tool and Agent Registry** (discovery dinámico, "yellow pages"), **Real-Time Compliance Monitoring** (governance automatizado, prevenir violaciones antes de que ocurran), **Agent Authentication and Authorization** (identidad y permisos verificables, IAM/OAuth 2.0), **Event-Driven Reactivity** (reaccionar a eventos asincrónicos vía message bus, no polling) — se encadenan en un ejemplo de supply chain. Conclusión: *production readiness is an architectural choice* — estos patrones son las decisiones deliberadas que atacan los requisitos no-funcionales (seguridad, escalabilidad, governance, fiabilidad) que separan una app robusta de un experimento frágil. El próximo capítulo (*Advanced Adaptation: Building Agents That Learn*) hace que los agentes mismos evolucionen más allá de instrucciones estáticas.

## Guía estratégica de implementación

### Mapeo de patrones system-level al GenAI Maturity Model (Tabla 10.1)

La pregunta recurrente ante estos patrones fundacionales es *"¿cuánto de esto necesito para empezar?"* — la respuesta depende de dónde estás en el viaje. Implementar un tool registry highly-available para un único agente no-crítico es **over-engineering**; desplegar un multi-agente que maneja data sensible sin authentication y compliance robustos es **negligente**. El Maturity Model da la hoja de ruta para alinear la implementación con las capacidades actuales y las ambiciones futuras.

| Nivel | Capacidades | Patrones habilitados | Resumen |
|---|---|---|---|
| **Nivel 3 – Agent-ready LLMs** | Foundational models y tools | Ideas iniciales sobre seguridad y reactividad: IAM básico (service accounts) y reactividad simple (webhooks) | Antes de desplegar agentes, las decisiones fundacionales sobre seguridad (integración IAM) y comunicación (event infrastructure) deben ser parte del diseño de plataforma. |
| **Nivel 4 – Single-agent systems** | Single agents production-grade | Agent Authentication and Authorization, Event-Driven Reactivity y Real-Time Compliance Monitoring | Cuando el primer agente entra a producción, la seguridad es no-negociable. El agente debe ser reactivo a su entorno, y si maneja tareas sensibles, el compliance monitoring se vuelve esencial. |
| **Nivel 5 – Multi-agent systems** | Ecosistemas de agentes colaborativos | Tool and Agent Registry | Apenas dos o más agentes necesitan colaborar dinámicamente, un registry se vuelve la piedra angular de la arquitectura, habilitando discovery y loose coupling en todo el sistema. |

El Maturity Model da el *cuándo* (secuencia y progresión de adopción); para el *dónde* hace falta entender cómo encajan en las capas funcionales.

### Arquitectura de integración del sistema: blueprint de production readiness

Los patrones system-level forman el *backbone operativo* de una aplicación agéntica completa. No son parte de ningún agente individual; proveen el entorno en el que todos los agentes operan segura y eficientemente:
- **API gateway (security & entry point)** — el único punto de entrada fortificado para todos los requests al sistema agéntico. *Patrón habilitado*: **Agent Authentication and Authorization**. Chequea firmas, expiración, audience claims y scopes, e impone token rotation para comunicación agente↔agente segura y de least-privilege.
- **Message bus / event stream (reactive backbone)** — el sistema nervioso central para comunicación asincrónica. *Patrón habilitado*: **Event-Driven Reactivity**. Los agentes sensan eventos corriendo como consumers continuos o vía conexiones de stream long-lived; cuando llega un evento nuevo a un topic suscrito, se dispara el componente `Sense` del agente, iniciando su reasoning loop. Permite reaccionar a cambios sin coupling directo.
- **Central registry (discovery & directory)** — las "yellow pages" del sistema, para discovery dinámico. *Patrón habilitado*: **Tool and Agent Registry**. Todos los agentes y tools descubribles registran acá sus capacidades y endpoints.
- **Governance services (oversight & compliance)** — una capa dedicada que observa y gobierna el comportamiento del agente. *Patrón habilitado*: **Real-Time Compliance Monitoring**. Un servicio/agente de compliance se suscribe al message bus o actúa de gateway para interceptar y adjudicar acciones contra un policy engine central. Impone constraints a nivel **action-level** (ej. `approve loan`), **row-level** (registros específicos) y **field-level** (ej. bloquear PII/PHI), asegurando compliance granular antes de que cualquier operación proceda.

### Pattern chaining en la práctica: ejemplo de supply chain automatizado

Recorrido de un evento de negocio de punta a punta, mostrando cómo los patrones trabajan en concierto para manejar un evento externo de forma segura y a escala:
1. **Event-Driven Reactivity** — un mensaje del webhook de un partner logístico externo se publica al topic `shipping_events` del message bus. El evento indica la llegada de un contenedor al puerto.
2. **Event-Driven Reactivity** — un `InventoryAgent` está suscrito a ese topic; el mensaje nuevo lo dispara a actuar. Su goal: verificar el contenido del contenedor y actualizar el inventario.
3. **Agent Authentication and Authorization** — para obtener el manifiesto del contenedor, el `InventoryAgent` necesita acceder al `ShippingAPI`; primero pide un access token al sistema IAM usando sus credenciales de service account.
4. **Agent Authentication and Authorization** — el `InventoryAgent` llama al `ShippingAPI` presentando su token; el API gateway intercepta la llamada, valida el token y confirma que el agente tiene el permiso `read:manifest`.
5. **Tool and Agent Registry** — tras procesar el manifiesto, el `InventoryAgent` determina que debe notificar a finanzas; consulta el Tool and Agent Registry para "encontrar un agente que pueda procesar customs payments". El registry devuelve el endpoint del `CustomsPaymentAgent`.
6. **Real-Time Compliance Monitoring** — el `InventoryAgent` manda un request al `CustomsPaymentAgent` para iniciar el pago. Un `ComplianceMonitor` intercepta este evento del message bus, chequea el monto contra su policy engine y verifica que el vendor esté en la lista aprobada, logueando un evento *compliance-checked*.
7. El `CustomsPaymentAgent` recibe el request validado y completa su tarea de forma segura.

> [!note] **Resiliency in action: handling a failure path** — Si el access token del `InventoryAgent` hubiera expirado durante el *Step 4*:
> - **Failure**: el `ShippingAPI` rechaza la llamada con un error `401 Unauthorized`.
> - **Recovery**: en vez de crashear, la lógica interna del agente atrapa ese código de error específico, se re-autentica automáticamente con el IAM, obtiene un token fresco y reintenta el request al `ShippingAPI`.
> - **Result**: el workflow se reanuda automáticamente, demostrando cómo los patrones de seguridad system-level trabajan con la robustez agent-level (cap. 7) para manejar interrupciones comunes.

### Guía para el rollout enterprise (Tabla 10.2)

Adoptar estos patrones requiere un enfoque deliberado y por fases; alinear la implementación con el maturity model asegura una base estable y segura antes de agregar complejidad.

| Fase | Patrones a implementar | Rationale |
|---|---|---|
| **Fase 1: Asegurar la base** | Agent Authentication and Authorization | Para el primerísimo agente en producción (Nivel 4), la seguridad es primordial. Integrá con tu sistema IAM enterprise desde el día uno. Tratá al agente como una *first-class service identity*. |
| **Fase 2: Habilitar reactividad y oversight** | Event-Driven Reactivity y Real-Time Compliance Monitoring | A medida que el sistema toma tareas más críticas, desacoplá componentes con un event bus para escalabilidad. Introducí compliance monitoring para cualquier workflow con data sensible, PII o transacciones financieras. |
| **Fase 3: Escalar el ecosistema** | Tool and Agent Registry | Cuando estés listo para un verdadero multi-agente (Nivel 5), un registry es requerido para gestionar la complejidad y habilitar colaboración dinámica entre agentes. |

## 1. Tool and Agent Registry

A medida que el ecosistema agéntico crece, el número de agentes especializados y tools disponibles puede expandirse rápido. Un enfoque estático y hardcoded —donde los agentes conocen de antemano las funciones de los demás— se vuelve frágil e imposible de mantener. Este patrón da una solución dinámica y escalable para *service discovery*.
- **Contexto** — fundamental para cualquier sistema multi-agente o tool-heavy donde se quiere promover loose coupling y permitir que el sistema evolucione. Es foundational para que los agentes descubran y aprovechen dinámicamente capacidades que no fueron explícitamente programados para conocer en design time.
- **Problema** — ¿cómo puede un agente encontrar la tool correcta u otro agente con la capacidad (y tool) requerida para completar una tarea, especialmente en un sistema grande y en evolución donde constantemente se agregan nuevas tools y agentes?
- **Solución** — un **registry** centralizado, un servicio que actúa de "yellow pages" de las capacidades del sistema: (1) **Registration** — al desplegarse, una tool/agente se registra, proveyendo metadata de sus capacidades (function name ej. `get_supplier_quote`, descripción en lenguaje natural, input/output schema y network endpoint); (2) **Discovery** — cuando un agente necesita una capacidad, consulta el registry en vez de una llamada hardcoded; puede buscar por nombre o, más potente, por significado semántico (ej. `Find a tool that can book a flight`); (3) **Invocation** — el registry devuelve una lista de servicios matcheantes y sus endpoints; el agente que pidió usa esa info para invocar el servicio directamente. El patrón **desacopla el conocimiento de una capacidad de su implementación**.
- **Ejemplo (sistema de procurement dinámico)** — un `ProcurementAgent` necesita una cotización para una parte. La empresa tiene múltiples formas: un API interno para vendors preferidos y una tool de web scraping para sitios públicos. (1) **Registration**: `PreferredVendorAPITool` y `WebScrapingQuoteTool` se registran, ambas anunciando una capacidad `get_quote`; (2) **Discovery**: el `ProcurementAgent` recibe "Get the best price for Part #XYZ", su LLM forma un plan que incluye conseguir quotes, y consulta el registry: `Find all tools with the get_quote capability`; (3) **Invocation**: el registry devuelve los endpoints de ambas tools; la lógica del agente decide llamarlas **en paralelo** para hallar el mejor precio. Si el mes próximo se agrega un `InternationalVendorAPITool`, **no hace falta cambiar nada** del `ProcurementAgent`: apenas se registra, el agente lo descubre y usa automáticamente. (Código: clase `ToolRegistry` con `register_tool(name, capability, endpoint, schema)` y `discover_tools(capability)` indexando por capacidad; el `ProcurementAgent.get_best_price` descubre, invoca todas y hace `min(results, key=lambda x: x["price"])` — `PreferredVendor` $95.00 vs `WebScraper` $98.50.)
- **Consecuencias** — *Pros*: **modularity y scalability** (capacidades nuevas sin cambiar una línea de los agentes existentes), **resilience** (si una tool/agente cae, el registry puede proveer alternativas, ruteando alrededor del fallo). *Cons*: **single point of failure** (el registry mismo; debe diseñarse para high availability y resiliencia), **overhead** (agrega un network hop extra para discovery → algo de latencia; además hay que mantenerlo).
- **Guía** — para casos simples, una DB compartida o incluso un JSON file bien mantenido sirve de registry. Para enterprise, herramientas dedicadas de service discovery como **Consul** o **etcd** son más robustas. La clave de un registry exitoso es un **schema de metadata rico y bien definido** para describir capacidades.

## 2. Real-Time Compliance Monitoring

En industrias reguladas (finanzas, salud, legal) los sistemas agénticos no pueden ser "black boxes": sus acciones deben ser auditables y adherir estrictamente a regulaciones externas y políticas internas. Este patrón da un mecanismo de governance continuo y automatizado.
- **Contexto** — esencial para cualquier sistema agéntico que maneje data sensible, ejecute transacciones high-stakes u opere en un dominio gobernado por regulaciones como GDPR, HIPAA o reglas de compliance financiero.
- **Problema** — ¿cómo asegurar que las acciones de los agentes autónomos adhieran continuamente a un set complejo y dinámico de reglas, **previniendo violaciones antes de que ocurran** en vez de solo detectarlas después del hecho?
- **Solución** — un **compliance monitor** dedicado y system-wide (otro agente especializado o un policy engine service), que actúa de capa de governance: (1) **Centralized policy engine** — definir todas las reglas/regulaciones en formato machine-readable usando un policy engine como **OPA (Open Policy Agent)**; (2) **Event interception** — el monitor se suscribe a un event bus system-wide o actúa de gateway para acciones críticas, inspeccionando cada evento significativo (ej. un agente pidiendo data, o comunicándose con una parte externa); (3) **Real-time adjudication** — para cada evento, el monitor consulta el policy engine para validar constraints context-aware que van más allá de la autorización estándar. Mientras AuthZ chequea si un agente *puede* acceder a un recurso (permiso), el compliance monitor chequea si *debería* permitírsele, según el estado actual (ej. *"Agent X tiene permiso para leer records, pero ¿tiene consentimiento de usuario válido para este propósito de research específico?"*); (4) **Enforcement** — si la acción es compliant, procede; si viola una política, el monitor la bloquea, loguea un compliance breach y puede disparar una alerta a un supervisor humano.
- **Ejemplo (agente de salud HIPAA-compliant)** — un `ResearchQueryAgent` busca records de pacientes que matcheen ciertos criterios para un estudio clínico. (1) **The action**: el agente intenta acceder a la DB de pacientes para `Patient #12345`; (2) **Interception**: un `HIPAAComplianceAgent` intercepta este request de acceso a data; (3) **Adjudication**: chequea su policy engine con el contexto — *Rule*: un record de paciente solo se accede si hay consentimiento explícito y auditable para "clinical research" en archivo; *Check*: el compliance agent consulta la consent database y encuentra que `Patient #12345` solo consintió uso de data para "billing purposes"; (4) **Enforcement**: el policy engine devuelve `DENY`; el `HIPAAComplianceAgent` bloquea la query, previniendo una violación HIPAA, loguea el intento denegado y levanta una alerta para review. (Código: `PATIENT_CONSENT_DB` con `Patient-12345: ["billing"]` y `Patient-67890: ["billing", "clinical_research"]`; `policy_engine_adjudicate` exige `"clinical_research" in consent_types` con *default deny*; el `HIPAAComplianceMonitor.intercept_and_adjudicate` corre antes de ejecutar — Scenario 1 (Patient-12345) → DENY, Scenario 2 (Patient-67890) → ALLOW.)
- **Consecuencias** — *Pros*: **trust y safety** (esencial para construir confianza y operar segura y legalmente; provee un audit trail de todas las acciones), **dynamic governance** (las políticas se actualizan en el engine central **sin redeployar los agentes**, adaptándose rápido a nuevas regulaciones). *Cons*: **performance overhead** (chequear cada acción contra un policy engine agrega latencia; aplicar juiciosamente a operaciones sensibles/críticas), **complexity** (requiere setup y mantenimiento de un policy engine separado y un set de reglas cuidadosamente armado).
- **Guía** — usar un policy language estándar como **Rego** (para OPA) es muy recomendado. Por eficiencia, no toda acción necesita chequearse: enfocarse en crear **policy "choke points"** para interacciones críticas (acceso a data stores, APIs externas, comunicación con usuarios). El compliance gobierna *qué acciones* se permiten, pero sus reglas se basan en *quién* las realiza — y para ser seguro el sistema no puede confiar en la identidad auto-proclamada del agente: debe poder probarla verificablemente. Eso lleva directo al siguiente patrón.

## 3. Agent Authentication and Authorization

Cuando los agentes pueden actuar autónomamente en nombre del sistema, un usuario o una organización, la seguridad es la preocupación primordial. Un agente no asegurado no es solo una vulnerabilidad: es un **riesgo existencial** para la aplicación (puede ser manipulado para filtrar data sensible, ejecutar transacciones fraudulentas o causar daño system-wide). Antes de confiarle cualquier tarea significativa hay que responder con **certeza criptográfica** dos preguntas: *¿quién es este agente?* (authentication) y *¿qué tiene permitido hacer?* (authorization).
- **Contexto** — requisito no-negociable para cualquier sistema agéntico que no sea un monolito simple y aislado. Crítico siempre que los agentes acceden a recursos controlados (APIs, DBs), interactúan con otros agentes de distinto nivel de privilegio, o realizan acciones con consecuencias en el mundo real.
- **Problema** — ¿cómo gestionar de forma segura las identidades de agentes e imponer controles de acceso para prevenir acciones no autorizadas, data breaches o tomas de control maliciosas de las capacidades del agente, en un entorno distribuido y dinámico?
- **Solución** — integrar el sistema con un framework **IAM (identity and access management)** robusto, tratando a los agentes como ciudadanos de primera clase con identidades digitales, como usuarios o servicios: (1) **Authentication (verificar identidad)** — cada agente recibe una credencial única y verificable al desplegarse, típicamente un **service account** que genera tokens criptográficos short-lived (ej. **JWTs / JSON Web Tokens**); todo request se firma con su token y el servicio receptor lo valida; (2) **Authorization (imponer permisos)** — una vez autenticado, el sistema chequea qué tiene permitido vía access control policies. Usando **RBAC (role-based access control)**, los agentes reciben roles (ej. `billing_analyst`, `read_only_reporter`) y los permisos se otorgan a los roles, no a agentes individuales; cuando un agente autenticado hace un request, el resource server chequea si su rol tiene el permiso requerido para esa acción específica.
- **High-security enhancements** — en entornos de máxima integridad, el flujo estándar **OAuth 2.0 client credentials** se combina con JWTs firmados validados contra un **JWKS (JSON Web Key Set)** rotativo; además puede imponerse **mTLS (mutual TLS)** para autenticar tanto al client agent como al servidor en la capa de transporte, previniendo intercepción de tokens y asegurando trust end-to-end.
- **Ejemplo (sistema de analytics multi-departamental)** — una empresa tiene un `CustomerDataAgent` central que guarda la DB principal de clientes, más un `SalesAgent` y un `MarketingAgent`. (1) **Authentication**: el `SalesAgent` necesita el purchase history de un cliente; genera un JWT desde su service account y lo incluye en el header del request al `CustomerDataAgent`; el API gateway valida la firma del token, confirmando que el request es legítimamente del `SalesAgent`; (2) **Authorization**: el gateway chequea su rol `sales_role`, consulta su ACL y ve que `sales_role` puede leer los campos `purchase_history` y `contact_info`. El `MarketingAgent` (con `marketing_role`) solo puede leer data anonimizada y agregada. Si el `SalesAgent` intentara acceder a un campo restringido (ej. payment details), el check de autorización falla y el request se deniega con `403 Forbidden`. (Código: `ROLE_PERMISSIONS` con `sales_role: [read_purchase_history, read_contact_info]` y `marketing_role: [read_aggregated_data]`; `CustomerDataAgent.get_data` chequea 401 si el rol no existe, 403 si la acción no está en sus allowed_actions, 200 si concede — Scenario 1 sales/purchase_history → ALLOW, Scenario 2 sales/payment_details → 403, Scenario 3 marketing/aggregated_data → ALLOW.)
- **Consecuencias** — *Pros*: **security** (garantías fundamentales: previene impersonation y asegura least privilege), **auditability** (log claro y auditable de qué agente hizo qué acción y cuándo). *Cons*: **infrastructure complexity** (montar y gestionar un IAM propio: service accounts, token issuance, policy definition → overhead operativo), **development overhead** (los devs deben implementar correctamente el manejo de tokens en su código).
- **Guía** — **no reinventes la rueda de seguridad**: implementar tu propio protocolo de auth es un anti-pattern común que lleva a breaches. Apalancá estándares enterprise battle-tested: **OAuth 2.0** para autorización y **OIDC (OpenID Connect)** para autenticación. Entendé el flujo **OAuth 2.0 M2M (machine-to-machine)** — como los agentes son servicios automatizados sin humano que ingrese password, el flujo apropiado es **client credentials**: (1) **Setup**: registrás el agente como client con tu authorization server (Okta, Microsoft Entra ID —ex Azure AD—, Google IAM) → recibís `client_id` y `client_secret`; (2) **Token request**: el agente presenta `client_id` y `client_secret` al token endpoint; (3) **Token issuance**: el server valida y emite un access token short-lived (típicamente JWT); (4) **API call**: el agente incluye el token en el header `Authorization`; (5) **Validation**: el resource server (o un API gateway delante) valida el token (autenticidad, no expirado) y chequea los scopes para autorizar la acción. **Centralizá el enforcement en un API gateway**: en vez de que cada agente implemente su propia validación de tokens, el gateway intercepta todos los requests entrantes, valida el JWT, hace checks iniciales de autorización y pasa el request validado (con identidad y permisos del agente) al servicio downstream — simplifica dramáticamente el código de cada agente.
- **Key resources** — **OAuth 2.0 website** (https://oauth.net/), **RFC 6749** (spec oficial del OAuth 2.0 authorization framework), **JWT debugger** (https://www.jwt.io/, para decodificar payload y verificar firma), **documentación del IdP (identity provider)** elegido (Okta, Auth0, Microsoft Entra ID, Google Cloud IAM — guías paso a paso del client credentials flow), **secrets management** (el `client_id`/`client_secret` nunca hardcodeados; usar HashiCorp Vault, AWS Secrets Manager o Google Secret Manager para almacenarlos y recuperarlos seguros en runtime).

## 4. Event-Driven Reactivity

Los agentes a menudo necesitan responder a cosas del mundo exterior en (casi) tiempo real: un email nuevo, un cambio de precio de una acción, un archivo subido. **Pollear** constantemente las fuentes en busca de updates es ineficiente y escala mal. Este patrón da una solución mucho más elegante y escalable.
- **Contexto** — usado cuando un sistema agéntico necesita ser responsivo a eventos asincrónicos e impredecibles de sistemas externos, usuarios u otros agentes. Es la base para construir aplicaciones reactivas y real-time.
- **Problema** — ¿cómo puede un sistema agéntico reaccionar eficientemente a triggers externos o internos **sin desperdiciar recursos en polling constante**?
- **Solución** — **invertir el flujo de comunicación**: construir el sistema sobre una arquitectura event-driven, facilitada por un message bus o event stream central. Tres componentes core: (1) **Event producers** — sistemas que generan eventos (un web server manejando un signup, un sensor IoT); publican un mensaje chico y self-contained describiendo el evento (ej. `{ "event_type": "new_user", "user_id": "123" }`) a un topic específico del bus; (2) **Message bus** — componente de infraestructura dedicado (**Apache Kafka, RabbitMQ, Google Cloud Pub/Sub**) que recibe los mensajes de los producers y los rutea a los consumers interesados; (3) **Event consumers (agentes)** — los agentes que reaccionan se suscriben a los topics que les importan; el bus les pushea los mensajes apenas se publican, disparando su loop sense-plan-act. El agente no pregunta *"¿hay algo nuevo?"*; el sistema le dice *"acá hay algo nuevo"*.
- **Controles operativos para resiliencia** (tres esenciales): **Backpressure** (mecanismos para que un flood de eventos no sature los rate limits del agente); **DLQs (dead-letter queues)** (capturan eventos malformados que harían crashear a los agentes, evitando que un "poison pill" bloquee la cola); **idempotency** (las acciones del agente deben diseñarse idempotentes, para que si el bus re-entrega un evento —común en sistemas distribuidos— el agente no ejecute la misma acción dos veces, ej. double-billing).
- **Ejemplo (sistema de customer support automatizado)** — cuando un usuario envía un ticket nuevo, el sistema usa un event bus para disparar instantáneamente múltiples procesos independientes; este modelo "push" permite a un `TriageAgent` y un `ArchivingService` reaccionar en tiempo real sin pollear una DB. (1) **Producer**: un usuario envía un ticket por un web form; el web server publica un mensaje al topic `new_tickets` en Kafka; (2) **Message bus**: Kafka recibe el mensaje y ve dos servicios suscritos; (3) **Consumers**: un `TriageAgent` recibe el evento → se dispara, lee el contenido, usa un LLM para clasificar prioridad/categoría (ej. `"Billing"`, `"Urgent"`) y publica un evento enriquecido al topic `triaged_tickets`; un `ArchivingService` también recibe el evento original e inmediatamente escribe una copia del ticket crudo a un data warehouse de largo plazo para analytics. El `TriageAgent` no tuvo que pollear: fue activado instantáneamente por el evento. (Código: `MessageBus` con `subscribe(topic, callback)` y `publish(topic, message)` que pushea a todos los callbacks suscritos; `TriageAgent` y `ArchivingService` se auto-suscriben a `new_tickets` en su `__init__`; el `WebServer.submit_ticket` publica; lógica simulada: `priority = "Urgent" if "payment" in content else "Medium"`.)
- **Consecuencias** — *Pros*: **scalability y decoupling** (sistema altamente escalable y desacoplado; los producers no necesitan saber quiénes son los consumers y viceversa; se agregan más agentes consumidores sin cambiar los producers), **responsiveness** (el sistema se vuelve altamente reactivo y opera casi en tiempo real, disparado por eventos al ocurrir). *Cons*: **complexity** (complejidad operativa de desplegar/gestionar un message bus; la programación asincrónica es más difícil de debuggear que un request-response simple), **guaranteed delivery** (hay que configurar bien el bus para manejar garantías de entrega —ej. "at least once"— y los fallos de mensajes).
- **Guía** — definí un **schema versionado y claro** para los payloads de eventos (ej. con **Avro** o **Protobuf**) para que producers y consumers se comuniquen confiablemente en el tiempo. Empezá con un **managed service** (Google Pub/Sub, Amazon SQS/SNS) para reducir la carga operativa antes de considerar self-hostear algo como Kafka.

## Para aplicar

- **Adoptar los patrones progresivamente, no todos de día uno** — mapear su necesidad al Maturity Model: IAM básico + event infra como decisiones de plataforma (Nivel 3); Auth + Event-Driven + Compliance al entrar el primer agente a producción (Nivel 4); Tool/Agent Registry al pasar a verdadero multi-agente (Nivel 5). Over-engineering y negligencia son los dos extremos a evitar.
- **Seguir el rollout en 3 fases** — Fase 1 asegurar la base (Auth/AuthZ, integrar IAM desde el día uno, agente como first-class service identity); Fase 2 reactividad + oversight (event bus para desacoplar + compliance monitoring para PII/financiero); Fase 3 escalar el ecosistema (registry para multi-agente).
- **Tool and Agent Registry** — "yellow pages" centralizado con registration/discovery (por nombre o semántica)/invocation; desacopla conocimiento de capacidad↔implementación; schema de metadata rico; Consul/etcd en enterprise; diseñar para HA (es single point of failure).
- **Real-Time Compliance Monitoring** — policy engine central machine-readable (OPA/Rego), event interception, adjudicación context-aware (no solo *can* sino *should*, ej. consentimiento), enforcement preventivo (bloquear antes del hecho + log + alerta); políticas actualizables sin redeploy; aplicar en choke points críticos para limitar el overhead.
- **Agent Authentication and Authorization** — tratar al agente como identidad de primera clase; OAuth 2.0 client credentials (M2M) + JWT short-lived + RBAC; high-security: JWKS rotativo + mTLS; centralizar validación en un API gateway; no reinventar seguridad; secrets en Vault/Secrets Manager, nunca hardcoded.
- **Event-Driven Reactivity** — invertir el flujo (push, no poll) con message bus (Kafka/RabbitMQ/Pub-Sub); producers/bus/consumers desacoplados; resiliencia con backpressure + DLQs + idempotency; schema de eventos versionado (Avro/Protobuf); empezar con managed service.
